    9. Layered Architecture and Data Access

    The previous examples stored their data in memory or in the cache. A real application stores it in a database and is organized into layers (see the diagram in the introduction):

    • the web layer (controllers, forms, views): read the request, call the business layer, select the view;
    • the business layer: business rules;
    • the DAO layer (Data Access Object): database queries.

    Each layer is aware only of the layer below it, and as few of its details as possible: the web layer is unaware of SQL, and the business layer is unaware of HTML. This separation makes each layer easier to understand, test, and evolve. Example 28 applies this to managing a list of people: it is, on a smaller scale, the management of doctors and clients from the case study.

    In [PHP], database access is organized across several layers:

    • The PDO extension (PHP Data Objects) of [PHP] defines a common interface for all DBMS extensions: open a connection, execute a SQL command, and read rows. Each DBMS has its own driver: [pdo_mysql] for [MySQL] (and [MariaDB]), included with [PHP];
    • The DBAL framework (Database Abstraction Layer) adds connection and transaction management, a query builder, type conversion, and translates errors from each DBMS into common exceptions (a uniqueness constraint violation becomes a [UniqueConstraintViolationException], regardless of the DBMS);
    • Doctrine ORM (Object-Relational Mapper) maps classes (entities) to database tables and transforms the retrieved rows into objects. It follows the so-called Data Mapper model: entities are ordinary objects that know nothing about the database; a separate object, the entity manager, reads and saves them. This is the difference between [Eloquent] and ORM (which is derived from [Laravel]), which follows the Active Record model (each object knows how to read and save itself, [$person->save()]).

    [Doctrine] does not belong to [Symfony]: it is an independent project, but ORM is the one recommended by [Symfony], and DoctrineBundle integrates it into the application. It is the equivalent of [JDBC], [JPA], and [Hibernate] in [Java] (which [Doctrine] was based on), [Entity Framework Core] into [C#], or [SQLAlchemy] into [Python]. Note a consequence of how [PHP] works: since nothing survives the request, each request opens its own connection to the database (upon its first request, SQL) and closes it upon termination. There is no connection pool as in [Java] or [Python]; opening a connection to [MySQL] on the same machine takes only a fraction of a millisecond.

    The example requires a running [MySQL] (or [MariaDB]) server: the appendix explains how to install one using [Laragon].

    <?php
// src/Entity/Person.php: a row of the [persons] table, a Doctrine ENTITY

namespace App\Entity;

use Doctrine\DBAL\Types\Types;
use Doctrine\ORM\Mapping as ORM;

// #[ORM\Entity]: the class is an entity; #[ORM\Table]: its table
#[ORM\Entity]
#[ORM\Table(name: 'persons')]
class Person
{
    // the primary key, generated by the database (AUTO_INCREMENT); null before the insertion
    #[ORM\Id]
    #[ORM\GeneratedValue]
    #[ORM\Column]
    private ?int $id = null;

    // the VERSION of the row: Doctrine increases it at each modification, and only
    // modifies the row if its version has not changed since it was read (optimistic
    // lock); the type of the column must be given explicitly
    #[ORM\Version]
    #[ORM\Column(type: Types::INTEGER)]
    private int $version = 0;

    // the columns: their SQL type is deduced from the PHP type (string: VARCHAR)
    #[ORM\Column(name: 'first_name', length: 30)]
    private string $firstName;

    #[ORM\Column(name: 'last_name', length: 30)]
    private string $lastName;

    #[ORM\Column]
    private int $age;

    public function __construct(string $firstName, string $lastName, int $age)
    {
        $this->edit($firstName, $lastName, $age);
    }

    public function edit(string $firstName, string $lastName, int $age): void
    {
        $this->firstName = $firstName;
        $this->lastName = $lastName;
        $this->age = $age;
    }

    public function getId(): ?int
    {
        return $this->id;
    }

    public function getVersion(): int
    {
        return $this->version;
    }

    public function getFirstName(): string
    {
        return $this->firstName;
    }

    public function getLastName(): string
    {
        return $this->lastName;
    }

    public function getAge(): int
    {
        return $this->age;
    }
}
    • lines 10–11: the attribute [#[ORM\Entity]] designates the class as an entity; [#[ORM\Table]] specifies the name of its table (otherwise, [Doctrine] would take the name of the class, [person]). [ORM] is an alias for the namespace [Doctrine\ORM\Mapping] (line 7): [use ... as ORM] allows attributes to be written in a shorthand form;
    • Lines 15–18: The primary key ([#[ORM\Id]]), generated by the database ([#[ORM\GeneratedValue]]: derived from [AUTO_INCREMENT], which is derived from [MySQL]). It is [null] until the entity has been inserted;
    • lines 23–25: the row version. The [#[ORM\Version]] attribute grants [Doctrine] the optimistic lock, described below;
    • lines 28–35: the columns. Each property marked [#[ORM\Column]] corresponds to the column of the same name; its type, SQL, is derived from the type [PHP] ([string]: [VARCHAR], of length [length]; [int]: [INT]). Unlike [Eloquent], the columns are declared: the class specifies exactly what the table contains;
    • lines 37–72: the entity is an ordinary class: a constructor, a method that modifies the person, and accessors. The properties are private: a person can only be modified through its methods. [Doctrine], on the other hand, reads and writes the properties directly (via reflection), without going through the constructor or the methods.

    In a standard project, the [bin/console make:entity] command from [MakerBundle] writes the entity, asking a few questions about its properties.

    <?php
// src/Dao/PersonsDao.php: the DAO layer, queries, no business rule

namespace App\Dao;

use App\Entity\Person;
use Doctrine\ORM\EntityManagerInterface;

class PersonsDao
{
    // Doctrine's ENTITY MANAGER: it reads and writes the entities
    public function __construct(private EntityManagerInterface $em)
    {
    }

    // SELECT ... FROM persons ORDER BY last_name, first_name
    /** @return list<Person> */
    public function list(): array
    {
        return $this->em->getRepository(Person::class)->findBy([], ['lastName' => 'ASC', 'firstName' => 'ASC']);
    }

    // SELECT ... FROM persons WHERE id = ?; null if the person does not exist
    public function read(int $id): ?Person
    {
        return $this->em->find(Person::class, $id);
    }

    // a person with the same first and last names, other than [$exceptId], written in DQL,
    // Doctrine's query language: it speaks of entities and properties, not
    // of tables and columns
    public function namesake(string $firstName, string $lastName, int $exceptId = 0): ?Person
    {
        return $this->em->createQuery(
            'SELECT p FROM App\Entity\Person p WHERE p.firstName = :firstName AND p.lastName = :lastName AND p.id <> :id')
            ->setParameters(['firstName' => $firstName, 'lastName' => $lastName, 'id' => $exceptId])
            ->setMaxResults(1)
            ->getOneOrNullResult();
    }

    // INSERT (new entity) or UPDATE (entity read, then modified): persist entrusts
    // the entity to the manager, flush sends the necessary SQL statements to the database
    public function save(Person $person): void
    {
        $this->em->persist($person);
        $this->em->flush();
    }

    // DELETE FROM persons WHERE id = ?
    public function delete(Person $person): void
    {
        $this->em->remove($person);
        $this->em->flush();
    }
}

    The DAO layer contains only queries, with no business logic. It receives the entity manager (line 12), which uses the connection from the current query and participates in the open transaction—if there is one—initiated by the business layer.

    • Lines 18–21: Each entity has a repository (repository), an object that retrieves it from the database: [getRepository]. Its method [findBy(criteria, orderBy)] returns the list of entities that match the criteria (in this case, none: all of them), in the requested order. (A repository also has [findAll], [findOneBy], [count].... ; an application can write its own repository class, with its own queries: this is what [make:entity] generates.) ;
    • lines 24–27: [find]: retrieval by primary key, or [null];
    • lines 32–39: a query written in DQL (Doctrine Query Language), the query language of [Doctrine]. It resembles SQL, but refers to entities and properties ([App\Entity\Person p], [p.firstName]), which [Doctrine] translates into tables and columns. The values are named parameters ([:firstName]), provided by [setParameters]: they are transmitted to the database separately and are never copied into the text of the SQL command, which makes SQL injection impossible. [setMaxResults(1)] limits the result to one line ([LIMIT 1]); [getOneOrNullResult] returns the found entity, or [null];
    • Lines 43–47: The record. [persist] assigns a new entity to the manager (an entity read by the manager has already been assigned to him); [flush] sends all necessary SQL commands to the database: a [INSERT] for a new entity, and a [UPDATE] containing only the modified columns for an entity that was read and then modified. The manager compares each entity it has read to its original state: this is change tracking. After a [INSERT], [Doctrine] stores the ID generated by the database in the entity;
    • lines 50–54: the deletion: [remove], followed by [flush], which triggers [DELETE].

    <?php
// src/Business/PersonsBusiness.php: the BUSINESS layer, the business rules, and only
// them. Each operation that writes is a TRANSACTION: committed (COMMIT) if the
// function ends normally, cancelled (ROLLBACK) if an exception comes out of it

namespace App\Business;

use App\Dao\PersonsDao;
use App\Entity\Person;
use Doctrine\DBAL\Exception\UniqueConstraintViolationException;
use Doctrine\ORM\EntityManagerInterface;
use Doctrine\ORM\OptimisticLockException;

class PersonsBusiness
{
    private const NAMESAKE = 'A person already has these first and last names.';

    private const MODIFIED = 'This record has been modified meanwhile: reload it.';

    private const UNKNOWN = 'This person does not exist (anymore).';

    public function __construct(private PersonsDao $dao, private EntityManagerInterface $em)
    {
    }

    /** @return list<Person> */
    public function list(): array
    {
        return $this->dao->list();
    }

    public function read(int $id): Person
    {
        return $this->dao->read($id) ?? throw new BusinessException(self::UNKNOWN);
    }

    public function add(PersonData $data): Person
    {
        // wrapInTransaction: the function is executed in a transaction
        return $this->transaction(function () use ($data) {
            // rule 1: no two persons with the same first and last names
            if ($this->dao->namesake($data->firstName, $data->lastName)) {
                throw new BusinessException(self::NAMESAKE);
            }
            $person = new Person($data->firstName, $data->lastName, $data->age);
            $this->dao->save($person);
            return $person;
        });
    }

    public function edit(int $id, int $version, PersonData $data): Person
    {
        return $this->transaction(function () use ($id, $version, $data) {
            $person = $this->read($id);
            // rule 2: we do not modify a record modified meanwhile by someone else
            if ($person->getVersion() !== $version) {
                throw new BusinessException(self::MODIFIED);
            }
            if ($this->dao->namesake($data->firstName, $data->lastName, $id)) {
                throw new BusinessException(self::NAMESAKE);
            }
            $person->edit($data->firstName, $data->lastName, $data->age);
            // Doctrine's UPDATE "WHERE id = ... AND version = ..." raises an
            // OptimisticLockException if it has modified no row (see transaction)
            $this->dao->save($person);
            return $person;
        });
    }

    public function delete(int $id): Person
    {
        return $this->transaction(function () use ($id) {
            $person = $this->read($id);
            $this->dao->delete($person);
            return $person;
        });
    }

    // the [$operation] function, executed in a transaction. Two errors of the
    // database are business errors: the uniqueness constraint (two simultaneous adds),
    // and the optimistic lock (two simultaneous edits)
    private function transaction(callable $operation): Person
    {
        try {
            return $this->em->wrapInTransaction($operation);
        } catch (UniqueConstraintViolationException $e) {
            throw new BusinessException(self::NAMESAKE, previous: $e);
        } catch (OptimisticLockException $e) {
            throw new BusinessException(self::MODIFIED, previous: $e);
        }
    }
}
    • lines 16–20: the business rule messages;
    • lines 32–35: a nonexistent person is a business error. The operator [??] accepts an expression [throw] on the right-hand side: if the person is [null], the exception is thrown;
    • lines 37–49: Rule No. 1: No two people may have the same first and last names. The rule is checked before writing to the database, and a [BusinessException] exception is thrown if it is not satisfied. But this check is not sufficient: two simultaneous requests could both verify that there are no namesakes, and then both proceed to insert the records. The database’s uniqueness constraint then rejects the second [INSERT], and [Doctrine] triggers a [UniqueConstraintViolationException], which the [transaction] method transforms into the same [BusinessException]. The database is the last line of defense;
    • lines 51–68: Rule No. 2: Do not modify a record that has been modified in the meantime by someone else. The update form carries the version of the record that was read (in a hidden field); if it differs from the current version, the record has changed since it was displayed. There remains the case where the concurrent modification occurs between the read in line 54 and the save in line 65: this is detected by the optimistic lock in [Doctrine]. For an entity that has a version, [UPDATE] checks two conditions—the ID and the read version—and increments the version by 1; if another query has modified the row in the meantime—its version has changed—the [UPDATE] lock does not modify any rows, and [Doctrine] releases a [OptimisticLockException] lock. This is the principle of optimistic locking: nothing is blocked, but concurrent modifications are detected. ([Doctrine] does this itself, as do [Hibernate] and [SQLAlchemy]; the [Laravel] version of this course had to write the condition by hand.);
    • lines 70–77: Deletion marks the person as deleted for the confirmation message;
    • Lines 82–91: Every operation that writes data is executed within a transaction: [wrapInTransaction] opens the transaction, executes the function, submits the pending changes ([flush]), then commits the transaction ([COMMIT]) and returns the function’s value; If an exception is thrown from the function, the transaction is rolled back ([ROLLBACK]): none of the changes made within the function are retained, and the exception is propagated. The business layer thus determines the scope of transactions: one business operation, one transaction. The two database errors that are business errors become [BusinessException]; the parameter named [previous] attaches the original exception to the new one for the log. Another error is returned as-is: it is not a business error, but a programming error (or a system failure). After an exception, [Doctrine] closes the entity manager, whose state is no longer reliable: it can no longer be used during the query, which is not a problem here, since the query is ending.

    The parameter [callable] of the method [transaction] refers to an arbitrary function; the anonymous functions on lines 40, 53, and 72 capture, via [use], the variables they need.

namespace App\Form;

use App\Entity\Person;
use App\Business\PersonData;
use Symfony\Component\Validator\Constraints as Assert;

class PersonInput
{
    #[Assert\NotBlank(message: 'The first name is required.')]
    #[Assert\Length(max: 30, maxMessage: '30 characters at most.')]
    public ?string $firstName = null;

    #[Assert\NotBlank(message: 'The last name is required.')]
    #[Assert\Length(max: 30, maxMessage: '30 characters at most.')]
    public ?string $lastName = null;

    #[Assert\NotNull(message: 'The age is required.')]
    #[Assert\Range(notInRangeMessage: 'The age must be between 0 and 150.', min: 0, max: 150)]
    public ?int $age = null;

    // the version of the record, carried by a hidden field (edit only)
    public ?int $version = null;

    // the input, pre-filled with an existing person
    public static function from(Person $p): self
    {
        $input = new self();
        $input->firstName = $p->getFirstName();
        $input->lastName = $p->getLastName();
        $input->age = $p->getAge();
        $input->version = $p->getVersion();
        return $input;
    }

    // the validated data, for the business layer
    public function data(): PersonData
    {
        return new PersonData(trim($this->firstName), trim($this->lastName), $this->age);
    }
}

However, the form would then modify the entity before the business layer had verified its rules, and an invalid entity would be passed to the entity manager. A separate input class keeps the layers distinct: the web layer transmits only validated data to the business layer.

    <?php
// src/Controller/PersonsController.php: the WEB layer; it only knows the business layer

namespace App\Controller;

use App\Form\PersonInput;
use App\Form\PersonType;
use App\Business\BusinessException;
use App\Business\PersonsBusiness;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\Form\FormInterface;
use Symfony\Component\HttpFoundation\Request;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\HttpKernel\Exception\AccessDeniedHttpException;
use Symfony\Component\Routing\Attribute\Route;

// name: a prefix for the name of all the routes of the class (persons_list...)
#[Route(name: 'persons_')]
class PersonsController extends AbstractController
{
    public function __construct(private PersonsBusiness $business)
    {
    }

    #[Route('/', name: 'home', methods: ['GET'])]
    public function home(): Response
    {
        return $this->redirectToRoute('persons_list');
    }

    #[Route('/persons', name: 'list', methods: ['GET'])]
    public function list(): Response
    {
        return $this->render('persons/list.html.twig', ['persons' => $this->business->list()]);
    }

    // GET: the empty form; POST: the sent form
    #[Route('/persons/add', name: 'add', methods: ['GET', 'POST'])]
    public function add(Request $request): Response
    {
        $input = new PersonInput();
        $form = $this->createForm(PersonType::class, $input);
        $form->handleRequest($request);
        if ($form->isSubmitted() && $form->isValid()) {
            try {
                $p = $this->business->add($input->data());
                $this->addFlash('success', "{$p->getFirstName()} {$p->getLastName()} has been added.");
                return $this->redirectToRoute('persons_list');
            } catch (BusinessException $e) {
                // a business rule refuses: the form is displayed again, with the
                // input, and the message, at the bottom of the page
                return $this->formPage('Add a person', $form, $e->getMessage());
            }
        }
        return $this->formPage('Add a person', $form);
    }

    // GET: the edit form, pre-filled
    #[Route('/persons/{id<\d+>}/edit', name: 'edit_form', methods: ['GET'])]
    public function editForm(int $id): Response
    {
        try {
            $p = $this->business->read($id);
        } catch (BusinessException $e) {
            $this->addFlash('error', $e->getMessage());
            return $this->redirectToRoute('persons_list');
        }
        return $this->formPage('Edit a person', $this->editFormFor($id, PersonInput::from($p)));
    }

    // PUT: the sent edit form
    #[Route('/persons/{id<\d+>}', name: 'edit', methods: ['PUT'])]
    public function edit(Request $request, int $id): Response
    {
        $input = new PersonInput();
        $form = $this->editFormFor($id, $input);
        $form->handleRequest($request);
        if ($form->isSubmitted() && $form->isValid()) {
            try {
                $p = $this->business->edit($id, (int) $input->version, $input->data());
                $this->addFlash('success', "{$p->getFirstName()} {$p->getLastName()} has been edited.");
                return $this->redirectToRoute('persons_list');
            } catch (BusinessException $e) {
                return $this->formPage('Edit a person', $form, $e->getMessage());
            }
        }
        return $this->formPage('Edit a person', $form);
    }

    #[Route('/persons/{id<\d+>}', name: 'delete', methods: ['DELETE'])]
    public function delete(Request $request, int $id): Response
    {
        if (! $this->isCsrfTokenValid("delete-person-$id", $request->request->getString('_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        try {
            $p = $this->business->delete($id);
            $this->addFlash('success', "{$p->getFirstName()} {$p->getLastName()} has been deleted.");
        } catch (BusinessException $e) {
            // no form to display again: the error also travels as a flash message
            $this->addFlash('error', $e->getMessage());
        }
        return $this->redirectToRoute('persons_list');
    }

    // the edit form: sent by the PUT method, to the /persons/{id} URL
    private function editFormFor(int $id, PersonInput $input): FormInterface
    {
        return $this->createForm(PersonType::class, $input, ['edit' => true,
            'method' => 'PUT', 'action' => $this->generateUrl('persons_edit', ['id' => $id])]);
    }

    private function formPage(string $title, FormInterface $form, ?string $error = null): Response
    {
        // a business error: the 422 code, as for an invalid form (see example 19)
        return $this->render('persons/form.html.twig',
            ['title' => $title, 'form' => $form, 'error' => $error],
            new Response(status: $error ? 422 : 200));
    }
}
    • line 18: The class attribute [#[Route]] prefixes only the route names here: the route named [list] is actually called [persons_list];
    • line 21: the business layer, the only layer known to the controller;
    • lines 38–56: the process, in three steps: form validation (input errors, Example 19); the call to the business layer (business rules); then the PRG schema, with a success flash message (Example 20). A [BusinessException] re-displays the form, along with the entered data and the exception message, which the template will display at the bottom of the page. Input errors and business logic errors are thus handled in the same way;
    • lines 59–69: the edit form, pre-filled with the retrieved person. If the person does not exist, the user is redirected to the list with a flash error message;
    • lines 72–88: the update, following the same pattern as the add operation;
    • lines 90–104: deletion, protected by a CSRF token unique to each person (example 21). There is no form to redisplay: any error is also conveyed in a flash message, [error];
    • lines 107–111: the edit form is submitted using the method PUT (option [method]: [form_start] then adds the hidden field [_method], Example 21), to URL [/persons/{id}] (option [action]);
    • lines 113–119: the form page. A business error is returned with code 422, indicating an invalid form.

    In a single transaction, we can see: the read of the record, the search for a namesake (the query DQL, translated to SQL), followed by [UPDATE]. This transaction modifies only the column that has changed ([age]), increments the version number, and sets the optimistic lock condition ([AND version = ?]). [Doctrine] then reads the new version again to save it to the entity. [flush] opens a transaction itself; since there is already one—the business layer transaction—it simply creates a savepoint ([SAVEPOINT]), a nested transaction that is committed ([RELEASE]) at the end of [flush].
