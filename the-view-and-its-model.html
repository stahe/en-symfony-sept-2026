    4. The View and Its Model

    Up to this point, actions generated their own responses: text, JSON, and a few HTML tags written as a string. In a MVC application, this is the role of a view: a file that describes the page HTML, with placesholders for the data passed to it by the action—the view’s model.

    [Symfony] uses the [Twig] view engine, created by the same team. A [Twig] view is a file whose name ends with [.html.twig] (the output format, followed by the engine), stored in the application’s [templates] folder. It is a text file—in this case, HTML—in which three types of tags are interpreted on the server:

    • [{{ expression }}]: the value of an expression, inserted into the page;
    • [{% instruction %}]: an instruction (tag); a condition ([{% if %}]); loop ([{% for %}]), template inheritance ([{% extends %}], [{% block %}]), inclusion ([{% include %}])...;
    • [{# comment #}]: a comment, which does not appear on the generated page.

    Everything else is copied as-is. The expressions are not written in [PHP], but in the language of [Twig], which is simpler and safer: [model.title] refers to the property [title] of the object [model] (or its method [getTitle()], or the key [title] of an array: [Twig] looks it up itself); filters transform a value ([name|upper] capitalizes a name); functions perform calculations ([path('home')] generates a URL). [Twig] thus resembles [Jinja2] ([Flask]), from which it drew inspiration, or the engine of [Django]; it differs from [Blade] ([Laravel]) and [Razor] ([ASP.NET Core]), which combine HTML with host language code. A [Twig] view cannot execute arbitrary [PHP] code: it can only display the data provided to it. This is by design: the application logic remains within the classes. A view is not interpreted with every request: when it is first used, [Twig] compiles it into a [PHP] class, stored in the [var/cache/dev/twig] folder, which it then reuses as long as the view remains unchanged. We’ll see what this file looks like.

namespace App\Controller;

use App\Model\PageModel;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Routing\Attribute\Route;

#[Route(methods: ['GET'])]
class ViewsController extends AbstractController
{
    // render: the Twig engine builds the page from the view
    // templates/views/index.html.twig and from the variables passed in the array (here
    // a single one, [model]); the produced page is the body of the response
    #[Route('/', name: 'index')]
    public function index(): Response
    {
        $model = new PageModel(
            'My first view',
            'This page was built by Twig, on the server.',
            date('H:i:s'));
        return $this->render('views/index.html.twig', ['model' => $model]);
    }

    // the same view with another model; or another view, with the 404 code
    #[Route('/hello/{name}', name: 'hello')]
    public function hello(string $name): Response
    {
        if ($name === 'unknown') {
            // the third parameter of render: the response to complete, here with the 404 code
            return $this->render('views/unknown.html.twig', ['name' => $name],
                new Response(status: Response::HTTP_NOT_FOUND));
        }
        $model = new PageModel(
            "Hello $name",
            'This time, the title of the page comes from the URL.',
            date('H:i:s'));
        return $this->render('views/index.html.twig', ['model' => $model]);
    }
}
    • Lines 20–23: The action builds the view template. The function [date], derived from [PHP], formats the current time: [H] formats the hours, [i] formats the minutes, and [s] formats the seconds;
    • Line 24: The [render] method of [AbstractController] instructs [Twig] to generate the page. The first parameter is the name of the view: the file path, relative to the [templates] folder. The second parameter is an associative array, where each key becomes a variable in the view—in this case, a single one: [model]. [render] returns an object [Response], whose body is the generated page (of type [text/html]);
    • lines 31–35: another view, with another variable ([name]). The third parameter of [render] is a response to be populated: in this case, a 404 response for a custom error page. [new Response(status: ...)] passes the code via a named parameter, while the other parameters retain their default values;
    • Lines 36–40: the same view as the [index] action, but with a different template. This is the benefit of separating actions from views: a single view can be used by multiple actions.

  <title>{{ model.title }}</title>

<body>
  {# set: a variable of the view; the reduce filter adds up the prices, the length filter counts the products #}
  {% set total = model.products|reduce((sum, p) => sum + p.price, 0) %}
  {% set count = model.products|length %}
  <h1>{{ model.title }}</h1>
  {# 1. display a value of the model; null is displayed as an empty string;
     the default filter replaces an empty value. This Twig comment does not appear
     in the produced page #}
  <p>1. Name: {{ model.name }} - nickname: [{{ model.nickname }}] [{{ model.nickname|default('none') }}]</p>
  {# 2. {{ }} escapes HTML; the raw filter inserts it as is #}
  <p>2a. {{ model.html }}</p>
  <p>2b. {{ model.html|raw }}</p>
  {# 3. a condition #}
  {% if model.loggedIn %}
    <p>3. You are logged in.</p>
  {% else %}
    <p>3. You are not logged in.</p>
  {% endif %}
  {# 4. a loop: the loop variable describes the state of the loop #}
  <p>4. Our products:</p>
  <ul>
    {% for product in model.products %}
      <li>no. {{ loop.index0 }}: {{ product.name }}, {{ product.price }} {{ model.currency }}
        {{ product.inStock ? '(in stock)' : '(sold out)' }}
        {% if loop.first %} - the first one{% endif %}
        {% if loop.last %} - the last one, seen by {{ model.name }}{% endif %}
      </li>
    {% endfor %}
  </ul>
  {# 5. the empty list: the else block of a for loop #}
  <p>5. Your cart:
    {% for p in model.cart %}<span>{{ p.name }}</span>{% else %} it is empty.{% endfor %}
  </p>
  {# 6. computed expressions, the set variables, and the number_format filter #}
  <p>6. {{ count }} products, for a total of {{ total }} {{ model.currency }};
    average price: {{ (total / count)|number_format(2, '.', ',') }} {{ model.currency }}</p>
  {# 7. an object inside an object, and a filter that converts to uppercase #}
  <p>7. Address: {{ model.address.street }}, {{ model.address.city|upper }}</p>
  {# 8. verbatim: a text that Twig copies without interpreting it #}
  <p>8. Braces displayed as is: {% verbatim %}{{ model.name }}{% endverbatim %}</p>
</body>
</html>
    • Lines 9–10: The [{% set %}] statement creates a variable in the view. The total price is calculated by the filter [reduce], which reduces an array to a single value (like [array_reduce], example 06): its function receives the accumulated value and the current element; [(sum, p) => sum + p.price] is an arrow function of [Twig]. The filter [length] returns the number of elements in an array (or characters in a string). These calculations should be reserved for presentation purposes: the calculation normally belongs to the action;
    • line 15: a [null] value is displayed as an empty string. The [default] filter replaces an empty (or missing) value with a default value;
    • lines 17–18: [{{ }}] escapes HTML (2a); the filter [raw], on the other hand, inserts the value as-is, without escaping it (2b). [raw] is reserved for HTML generated by the application itself, never for user input;
    • Lines 20–24: a condition: [{% if %}], [{% elseif %}], [{% else %}], [{% endif %}]. Each block is closed by a [{% end... %}] statement;
    • Lines 28–34: a loop [{% for ... in ... %}] ... [{% endfor %}]. Within the loop, the special variable [loop] describes the loop’s state: [loop.index0] (the iteration number, starting at 0), [loop.index] (starting at 1), [loop.first], [loop.last] (true on the first and last iterations), [loop.length] (the number of elements). Variables outside the loop ([model.name]) remain accessible;
    • line 30: the ternary operator [condition ? a : b] ([Twig] also accepts [condition ? a], which returns an empty string if the condition is false);
    • line 38: a loop [for] can have a block [{% else %}], which is executed if the list is empty. This is simpler than a [{% if %}] that would check the length of the list;
    • lines 41–42: calculated expressions ([total / count]) and the variables from [set]. The filter [number_format] formats a number: two decimal places, a point as the decimal separator, and a comma as the thousands separator. In Example 16, we’ll see a much better way to format numbers and amounts;
    • line 44: the period passes through objects ([model.address.city]), and the filter [upper] capitalizes a string (while correctly handling accented characters);
    • line 46: the [{% verbatim %}] instruction copies its content without interpreting it: this is useful when a page contains curly braces intended for a [JavaScript] framework.

    [Twig] has about fifty filters ([lower], [capitalize], [trim], [join], [split], [slice], [sort], [date], [json_encode], [escape]...), about fifteen functions ([range], [min], [max], [random]...) and tests ([is defined], [is empty], [is null], [is iterable], [is even]...); the bundles for [Symfony] add some ([path], [asset], [form_row], [is_granted]...), and the application can write its own (Example 16).

        return $response;

// src/Twig/FormatsExtension.php: a Twig EXTENSION, which adds two filters
// to the language of the views: money and long_date

namespace App\Twig;

use DateTimeInterface;
use IntlDateFormatter;
use NumberFormatter;
use Symfony\Component\HttpFoundation\RequestStack;
use Twig\Extension\AbstractExtension;
use Twig\TwigFilter;

class FormatsExtension extends AbstractExtension
{
    // the request stack, to know the language of the current request
    public function __construct(private RequestStack $requests)
    {
    }

    // the filters of the extension: their name in the views, and the method that implements them
    public function getFilters(): array
    {
        return [
            new TwigFilter('money', $this->money(...)),
            new TwigFilter('long_date', $this->longDate(...)),
        ];
    }

    // an amount in cents, in a currency, in the format of the language of the
    // request: 114990 -> "€1,149.90" in English, "1 149,90 €" in French.
    // PHP's intl extension knows the conventions of each country
    public function money(int $cents, string $currency = 'EUR'): string
    {
        $formatter = new NumberFormatter($this->language(), NumberFormatter::CURRENCY);
        return $formatter->formatCurrency($cents / 100, $currency);
    }

    // a date in full words, in the language of the request: "Sunday, September 27, 2026"
    public function longDate(DateTimeInterface $day): string
    {
        $formatter = new IntlDateFormatter($this->language(), IntlDateFormatter::FULL, IntlDateFormatter::NONE);
        return $formatter->format($day);
    }

    private function language(): string
    {
        return $this->requests->getCurrentRequest()?->getLocale() ?? 'en';
    }
}

    public function search(Request $request): Response

            && ($genre === '' || $book->genre === $genre)));

    4.8. Example 20: The Post/Redirect/Get Pattern

    When a POST action responds with a page, that page is the result of a POST. If the user reloads the page (presses [F5]), the browser sends the POST request, after displaying a warning that few people read: the command is sent twice, and the message is posted twice. The Post/Redirect/Get pattern (PRG) avoids this problem: a successful POST action does not return a page; it responds with a redirect (example 04) to a page GET, which the browser requests immediately. Reloading this page simply re-executes the GET action.

    One problem remains: the GET page would like to display a message (“the task has been added”), but it is the POST action that knows this message, and it cannot pass a variable to a request that has not yet occurred. The solution: the flash message, placed in the session by the action POST, is retained until it is read, displayed, and then discarded.

// src/Service/TasksService.php: the list of the tasks, shared by all the
// users. In PHP, the objects do not survive the request: the list is
// stored in the CACHE of the application (here, a file of the var/cache/dev/pools folder)

namespace App\Service;

use Psr\Cache\CacheItemPoolInterface;
use Symfony\Component\Lock\LockFactory;

class TasksService
{
    private const KEY = 'tasks';

    // the cache of the application (the cache.app service) and the lock factory
    public function __construct(
        private CacheItemPoolInterface $cache,
        private LockFactory $locks,
    ) {
    }

    /** @return list<string> */
    public function list(): array
    {
        // the cache item stored under the [tasks] key; isHit: it exists
        $item = $this->cache->getItem(self::KEY);
        return $item->isHit() ? $item->get() : ['Read chapter 3'];
    }

    public function add(string $label): void
    {
        // several requests can run AT THE SAME TIME (the server handles
        // them in several processes): a lock guarantees that only one at a
        // time reads, modifies and rewrites the list
        $lock = $this->locks->createLock('tasks');
        // acquire(true): wait until the lock is free, then take it
        $lock->acquire(true);
        try {
            $tasks = $this->list();
            $tasks[] = $label;
            // the cache item receives its new value, without any time limit
            $item = $this->cache->getItem(self::KEY);
            $this->cache->save($item->set($tasks));
        } finally {
            // finally: the lock is released in all cases, even after an exception
            $lock->release();
        }
    }
}

    The task list is shared by all users and must persist from one request to the next. In [Java], [C#], or [Python], it would be kept in memory within a single service. In [PHP], this is impossible: as we saw in examples 01 and 06, nothing survives the request. The list must therefore be stored outside of [PHP]: in a database, a file... or in the application cache, which we are using here.

    • Lines 16–20: The service receives two services from [Symfony]. The first is the application cache (the [cache.app] service, from the Cache component), a store of key-value pairs, represented by the standardized interface [CacheItemPoolInterface] (the PSR-6 standard). By default, it stores its values in files within the [var/cache/dev/pools] folder; in production, a dedicated server is preferred, such as [Redis] (a configuration line). The second is the lock factory of the Lock component;
    • lines 23–28: [getItem] retrieves the cache item stored under a key; [isHit] checks if it exists, and [get] returns its value. Any value (in this case, an array of strings) can be stored: [Symfony] serializes it—that is, it converts it to text—using the function [serialize] from [PHP];
    • Lines 35–47: The development server, like a production server, can process multiple requests at the same time, across multiple processes (the environment variable [PHP_CLI_SERVER_WORKERS] sets the number of processes to [php -S]).                 new Contact(2, 'Paul Martin', '06 12 34 56 78'),
                new Contact(3, 'Philippe Jandot', '02 98 76 54 32'),
            ],
            'lastId' => 3,
        ];
    }

    // a modification of the data, under lock: the function receives the data,
    // modifies them (&), and returns the result of the operation
    private function editData(callable $operation): mixed
    {
        $lock = $this->locks->createLock('contacts');
        $lock->acquire(true);
        try {
            $data = $this->data();
            $result = $operation($data);
            $this->cache->save($this->cache->getItem(self::KEY)->set($data));
            return $result;
        } finally {
            $lock->release();
        }
    }

    /** @return list<Contact> */
    public function list(): array
    {
        return $this->data()['contacts'];
    }

    // the contact, or null if it does not exist
    public function read(int $id): ?Contact
    {
        return array_find($this->list(), fn (Contact $c) => $c->id === $id);
    }

    public function edit(int $id, string $name, string $phone): ?Contact
    {
        return $this->editData(function (array &$data) use ($id, $name, $phone) {
            foreach ($data['contacts'] as $i => $contact) {
                if ($contact->id === $id) {
                    // a contact is immutable (readonly): we build a new one,
                    // which replaces the old one in the array
                    return $data['contacts'][$i] = new Contact($id, $name, $phone);
                }
            }
            return null;
        });
    }

    public function add(string $name, string $phone): Contact
    {
        return $this->editData(function (array &$data) use ($name, $phone) {
            $contact = new Contact(++$data['lastId'], $name, $phone);
            $data['contacts'][] = $contact;
            return $contact;
        });
    }

    public function delete(int $id): ?Contact
    {
        return $this->editData(function (array &$data) use ($id) {
            foreach ($data['contacts'] as $i => $contact) {
                if ($contact->id === $id) {
                    // array_splice removes item i from the array, and renumbers the following ones
                    array_splice($data['contacts'], $i, 1);
                    return $contact;
                }
            }
            return null;
        });
    }
}

    The contacts are stored in the cache, just like the tasks in Example 20. Each contact is an immutable object [Contact] (an ID, a name, a phone number), stored in an array, with the most recently assigned ID. A few points about [PHP]:

    • lines 37–49: All modifications follow the same pattern: acquire the lock, read the data, modify it, write it back, and release the lock. This method writes to the array once; each modification passes it a function (of type [callable], “callable”), which receives the data and modifies it. The function must modify the array itself, not a copy: its parameter is declared as [array &$data], where [&] specifies a pass-by-reference (without [&], an array is copied; see Example 06). The keyword [use] in an anonymous function gives it access to variables in the containing function (line 65: [$id], [$name], [$phone]);
    • line 44: the calls follow one after another: [getItem] returns the element, [set] assigns a value to it and returns the element itself, [save] stores it;
    • lines 63–75: A contact is immutable: a new one is created, which replaces the old one in the array. An assignment is an expression whose value is the assigned value: [return $data['contacts'][$i] = new Contact(...)] replaces the contact and returns it;
    • line 80: [++] placed before a variable increments it by 1 and returns the new value;
    • line 92: [array_splice] removes an element from the array and renumbers the subsequent elements;
    • The methods return [null] for a nonexistent contact: it is up to the controller to decide on the response.

    {
        $contact = $this->contactOr404($this->contacts->read($id));
        $form = $this->createForm(ContactType::class,
            ['name' => $contact->name, 'phone' => $contact->phone]);
        $form->handleRequest($request);
        if ($form->isSubmitted() && $form->isValid()) {
            ['name' => $name, 'phone' => $phone] = $form->getData();
            $duplicate = $form->get('duplicate');
            // isClicked: the button that sent the form
            if ($duplicate instanceof SubmitButton && $duplicate->isClicked()) {
                $copy = $this->contacts->add("$name (copy)", $phone);
                $this->addFlash('success', "The contact [$copy->name] has been created.");
            } else {
                $this->contacts->edit($id, $name, $phone);
                $this->addFlash('success', "The contact [$name] has been edited.");
            }
            return $this->redirectToRoute('contacts');
        }
        return $this->render('contacts/details.html.twig', ['contact' => $contact, 'form' => $form]);
    }

    // a DELETE request, simulated by a POST form (hidden _method field)
    #[Route('/{id<\d+>}', name: '_delete', methods: ['DELETE'])]
    public function delete(Request $request, int $id): Response
    {
        // the anti-CSRF token of the form, specific to this contact
        if (! $this->isCsrfTokenValid("delete-contact-$id", $request->request->getString('_token'))) {
            throw new AccessDeniedHttpException('invalid anti-CSRF token');
        }
        $contact = $this->contactOr404($this->contacts->delete($id));
        $this->addFlash('success', "The contact [$contact->name] has been deleted.");
        return $this->redirectToRoute('contacts');
    }
}

// Without JavaScript, these forms are simply sent without confirmation.
(() => {
  const modal = document.getElementById('confirmation-modal');
  const message = document.getElementById('confirmation-modal-message');
  let pending = null; // the form to send if the user confirms

  // 1. we intercept the submission of the forms to confirm
  document.querySelectorAll('form[data-confirmation]').forEach((form) => {
    form.addEventListener('submit', (event) => {
      event.preventDefault(); // the submission is suspended
      pending = form;
      message.textContent = form.dataset.confirmation;
      modal.classList.remove('d-none'); // the window appears
    });
  });

  // 2. the two buttons of the window
  modal.addEventListener('click', (event) => {
    const action = event.target.dataset.action;
    if (action === 'yes') {
      pending.submit(); // submission, WITHOUT firing the 'submit' event again
    } else if (action === 'no') {
      modal.classList.add('d-none');
      pending = null;
    }
  });
})();
    • line 3: the code is enclosed in an anonymous function, which is executed immediately; its variables do not interfere with those of the other scripts on the page;
    • lines 4–6: the window, the message location, and the form awaiting confirmation;
    • lines 9–17: for each form that has a [data-confirmation] attribute, the [submit] event—triggered when the form is submitted—is intercepted. [preventDefault()] suspends submission; the form is put on hold, and its message ([dataset.confirmation], the value of the [data-confirmation] attribute) is displayed in the window, which appears;
