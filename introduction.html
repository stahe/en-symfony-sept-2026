    This document is a product of Anthropic’s IA Claude. It follows the document “Step-by-Step Introduction to the [Laravel] Web Framework” (2026), which itself followed the documents “Step-by-Step Introduction to the [Flask] Web Framework,” "Step-by-Step Introduction to the [Spring MVC] Web Framework," "Step-by-Step Introduction to the [ASP.NET Core MVC] Web Framework," and "Step-by-Step Introduction to the [NestJS] Web Framework" (2026). This document remains within the [PHP] universe but changes frameworks:

    • the [Laravel] framework is replaced by the [Symfony] 8.1 framework, still using the [PHP] language (version 8.4 or later);
    • the [Blade] views are replaced by [Twig] views, the view engine for [Symfony];
    • Validation using the rules in [Laravel] and form queries ([FormRequest]) is replaced by the Validator component in [Symfony] (constraints, written as [PHP] attributes) and by its Form component, which describes forms using classes;
    • the guards, middleware, and [Gate] components of [Laravel] are replaced by the Security component of [Symfony]: firewalls, authenticators, roles, password hashing, and an attempt limiter, supplemented by the [firebase/php-jwt] library for JWT tokens;
    • Middleware components, however, do not exist in [Symfony]: event listeners are used to intervene in request processing;
    • ORM [Eloquent] is replaced by [Doctrine], ORM is based on [Symfony], which in turn is based on [MySQL].

    The document closely follows the structure of the [Laravel] course: first, numerous small projects, each focused on a single concept, followed by a comprehensive case study—a web application for scheduling appointments at a medical practice—with all files fully commented. The examples have the same numbers and cover the same topics as in courses [Laravel], [Flask], [Spring MVC], and [ASP.NET Core MVC]: A reader familiar with one of these courses can compare the frameworks on a case-by-case basis. However, this is not necessary: this document stands on its own and assumes no prior knowledge of these frameworks. The only prerequisites are a basic understanding of web programming (the HTTP protocol, the HTML language) and the fundamentals of the [PHP] language (variables, arrays, functions, classes). The course “Introduction to the PHP7 Language Through Examples” (2019) introduces the language itself for those who need to learn it first; the new features of [PHP] 8 used here (promoted properties, [readonly] classes, attributes, enumerations, named arguments, the null-safe operator, etc.) are explained when they first appear.

    1.1. Symfony’s Role in a Web Application

    A web application is often built in layers, with each layer communicating only with its neighboring layers:

    • the web layer receives requests HTTP from the browser and returns pages HTML to it. This is the layer that [Symfony] helps us write;
    • the business layer contains the application’s business rules (e.g., “a patient can have only one upcoming appointment”). It knows nothing about the web: it could just as easily serve a command-line application;
    • the data access layer (DAO layer, for Data Access Object) reads from and writes to the database. We will use [Doctrine], the ORM (Object Relational Mapper) associated with [Symfony], which maps table rows to [PHP] objects.

    The web layer itself follows the MVC (Model-View-Controller) pattern:

    • the controller (C) is a class [PHP] whose methods, called actions, each handle a specific type of request (for example, [GET /agenda]). An action reads the request parameters, processes the request through the business layer, and then selects the view to display;
    • the model (M) is the set of data that the action passes to the view;
    • the view (V) is a [Twig] file (extension [.html.twig]): a HTML page that contains [{{ ... }}] expressions and [{% if %}], [{% for %}]... instructions, which the [Twig] engine replaces with data from the template.

    A note on terminology, to avoid confusion: in [Symfony], the classes that represent database tables are called entities (document [src/Entity]). In this document, the term “model” will therefore always refer to the view model (the data passed to a view) or, in Chapter 2, the action model (the data it receives). The term “template” refers to the common view from which other pages inherit (chapter on views).

    The processing of a request follows the numbered steps in the diagram:

    • 1: The browser sends a request, such as HTTP or [GET /agenda?idMedecin=1&jour=2026-09-26];
    • 2: The web server receives the request and passes it to the [Symfony] application via the [public/index.php] file. During development, this server is the one that includes [PHP], launched by the command [php -S localhost:8000 -t public]; in production, it will be a server such as [nginx] or [Apache], associated with [PHP-FPM]. The file [public/index.php] passes the request to the application’s kernel (kernel), which routes it through a series of events: classes from [Symfony] and the application, as well as listeners (session, security, language, etc.), are involved. One of them compares the requested path to the application’s routes and selects the action responsible for this request: this is routing;
    • 3: The action requests the data it needs from the business layer; if necessary, the business layer contacts the DAO layer, which queries the [MySQL] database in SQL;
    • 4: The action constructs the view’s M model and instructs the [Twig] engine to generate the page (method [render]);
    • 5: The page HTML generated by the view is the action’s response, which [Symfony] returns to the browser.

    [Symfony] is, along with [Laravel], one of the two major web frameworks in the [PHP] world. Free and open-source, created in 2005 by Fabien Potencier (and the French company SensioLabs), it works anywhere that [PHP] ([Windows], [Linux], [macOS]), and [PHP] works with almost all web hosting providers. [Symfony] is primarily a collection of about fifty components—independent libraries (HTTP requests and responses, routing, the console, forms, validation, security, etc.)— so well-regarded that other projects use them: [Laravel] itself is built on several of them, and readers of the previous lesson have already encountered them. The [Symfony] framework assembles these components using bundles (integration packages) and a service container that creates the application’s objects. Compared to [Laravel], [Symfony] makes clear choices: no facades or global functions, but services obtained through dependency injection; explicit configuration in YAML files; [PHP] attributes ([#[Route]], [#[Assert\NotBlank]]...) to describe the code; a ORM and [Doctrine], which separate objects from their registration. It is a framework renowned for its rigor, its documentation, and its versioning policy: a minor release every six months, a “long-term support” release every two years, and the guarantee that an application without an obsolescence warning will transition to the next major version without modification. [Symfony] can create servers that return JSON to a [JavaScript] client ([Angular], [React], [Vue.js], [Flutter]...) as well as traditional web applications, where the server generates the HTML pages and the browser simply displays them. It is this second use case that this document examines.

    A specific feature of [PHP] explains a great deal about [Symfony]: the application is rebuilt with each request and then discarded (example 01). [Symfony] offsets this cost by compiling its configuration once and for all into [PHP] code, which is stored in a cache ([var/cache] folder). We will return to this frequently.

    1.2. Tools Used

    The examples were written and tested using the following tools (their installation is described in the appendix):

    • [PHP] 8.4 (any version 8.4 or later is suitable), with the extensions [intl], [mbstring], [openssl], and [pdo_mysql];
    • [Composer] 2, the library manager for [PHP];
    • the editor [Visual Studio Code], with the extensions [PHP Intelephense] (code analysis), [Twig Language 2] (views), and [YAML] (configuration files);
    • a modern browser ([Chrome], [Firefox], [Edge]);
    • the command-line tool [curl], which displays the raw HTTP responses (it is included with [Windows] 10 and 11);
    • SGBD, [MySQL] (or [MariaDB]), for example, that of [Laragon] under [Windows], starting with the chapter on data access, and for the case study. Under [Windows], [Laragon] installs [PHP], [Composer], and [MySQL] all at once.

    [Symfony] is typically installed by creating a complete project using the command:

    1
    composer create-project symfony/skeleton mon-projet

    or using the [Symfony] command-line tool (the [symfony] program; see appendices): [symfony new mon-projet --webapp]. [Composer] then downloads the skeleton of a [Symfony] application, followed by its libraries. The skeleton also contains [Symfony Flex], a plugin for [Composer] that, each time a library ([composer require twig]) is installed, writes its own configuration files based on templates published online. This is how you start a real project. For learning purposes, this method has a drawback: the files appear on their own, without you knowing what they’re for. The examples in this document therefore start from the other end: Example 01 is the smallest possible [Symfony] application, and each example adds only the files it needs, written and commented on by hand. The case study at the end follows the structure of a standard [Symfony] application.

    The database [dbrdvmedecins] has been created. Here is its content:

    • in [1-3], the table [clients];
      • [id] is the primary key of the table;
      • [version] is the row’s version number. This number increments each time the row is modified;
      • [titre, nom, prenom] identifies the person;

    • in [1-3], the table [medecins];
      • [id] is the primary key of the table;
      • [version] is the version number of the row;
      • [titre, nom, prenom] identifies the person;

    • In [1-3], the table of doctors’ appointment time slots:
      • [id]: primary key;
      • [version]: row version number;
      • [id-medecin]: foreign key referencing the doctor’s primary key;
      • [hdebut, mdebut]: hour and minutes of the appointment start time. Thus, [8,20] means 8:20 a.m.
      • [hfin, mfin]: hour and minutes of the end of the consultation.

    • In [1-3], the [rv] table of scheduled appointments;
      • [id]: primary key;
      • [version]: version number;
      • [jour]: appointment date;
      • [id_creneau]: foreign key referencing the primary key of the appointment time slot. Since a time slot is linked to a doctor, we know which doctor is handling this appointment;

      • [login, password]: user credentials;
      • [nom]: user name;

    An application with the ID [PHP] fails to read the database upon startup: a connection error only appears on the first page that queries the database, i.e., at the time of connection. [Symfony] then displays its detailed error page and logs the error to the server console. If the message is [SQLSTATE[HY000] [2002] Connection refused], it means that [MySQL] has not started; with [[1045] Access denied for user 'root'@'localhost'], it means the password is incorrect; with [[1049] Unknown database 'dbrdvmedecins2'], it means the script SQL was not executed; with [could not find driver], that the [pdo_mysql] extension of [PHP] is not enabled. If the page displays [Failed opening required '.../vendor/autoload_runtime.php'], it means that [composer install] was not executed; if the [php -S] command fails with the message [Failed to listen on localhost:8081 (reason: Address already in use)], it means that port 8081 is already in use (by another version of the application, for example). The application’s [README.md] file describes other scenarios. Stop the application using [Ctrl-C] in the terminal.
